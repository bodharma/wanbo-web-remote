# Прошивка T2M+: CPU TvService та USB/Wi-Fi

[English](FIRMWARE_TUNING.md) · **Українська** · [Програми й налаштування](PROJECTOR_SETUP.uk.md)

Ці результати стосуються одного Wanbo T2M+ з Android 9 / API 28, прошивкою `9.0.0-RS-20210928.1224` та 32-бітним ARM userspace. Інші ревізії T2 Max можуть мати іншу плату, розділи та політики перевірки. Самого збігу назви моделі недостатньо.

Вебпульт працює незалежно від цих необов'язкових змін прошивки. Docker і браузер не встановлюють патч, не перемонтовують розділи Android і не змінюють USB/Wi-Fi. Репозиторій містить результати та source-diff без OEM APK, образів прошивки, ключів підпису чи автоматичного інсталятора прошивки.

## Результати вимірювань

| Спостереження | Результат на перевіреному пристрої |
| --- | --- |
| CPU штатного TvService | Приблизно 103% одного ядра за 5,4 секунди; близько 94% припадало на температурний потік |
| CPU після зміни | Медіана 0,19%, максимум 0,26% одного ядра протягом 15 хвилин |
| Вибіркова перевірка доступності | 57 успішних перевірок Wi-Fi/ADB; PID і час старту служби не змінювалися |
| Температурна властивість | 38–46°C за час спостереження |
| Збереження змін | Змінений APK і USB-конфіг `host` були присутні після завершеного нового запуску |

Відсотки CPU наведені для одного ядра: 100% означає одне зайняте ядро, а не весь чотириядерний процесор. Спостереження включало звичайний перегляд Jellyfin. Перевірки лише читали стан: не призупиняли відео, не надсилали кнопки й не перезапускали застосунки. Це вибіркова перевірка одного пристрою, а не безперервний вимір втрат пакетів чи багатогодинний тест. Реального перегріву не створювали.

## Діагностика без змін

Використовуйте авторизовану ADB-сесію з [гайда налаштування](PROJECTOR_SETUP.uk.md). Ці команди не змінюють проєктор:

```sh
adb shell getprop ro.product.model
adb shell getprop ro.build.version.sdk
adb shell getprop ro.product.cpu.abi
adb shell 'dumpsys cpuinfo | grep com.toptech.tv.service'
adb shell 'tr " " "\n" < /proc/cmdline | grep "^USB_OTG_SOFTWARE_ID="'
adb shell 'grep -E "^(cfg80211|8723du) " /proc/modules'
adb shell ip link show wlan0
adb shell sha256sum /system/app/TvService/TvService.apk
```

Зберігайте приватно сирі журнали, серійні номери, MAC-адреси, локальні адреси сервісів і дані акаунтів. Android root і права контейнера — різні речі. На цій прошивці `/system` був частиною кореневої файлової системи (`/`), а `/vendor` — окремим монтуванням; звіряйте фактичні точки монтування. Вбудовані CLI-утиліти також відрізняються від настільних GNU: `stat` цієї прошивки не підтримує `%r` і повертав для нього `?`. Для перевірки розділів використовували `/proc/self/mountinfo` та звірені ідентифікатори пристроїв.

## TvService: пауза в температурному циклі

Заводський `com.toptech.tv.service.TvService$5.run()` без паузи зчитував `mid.data.about.temperature`. Це займало ядро й створювало роботу для виділення пам'яті та GC. Функціональна зміна — **`SystemClock.sleep(100L)` у спільному кінці циклу**, після наявної перевірки. Перше зчитування температури залишається негайним; між наступними ітераціями є пауза 100 мс. Наявна **гілка захисту при 80°C збережена**.

Точна зміна наведена в [tvservice-temperature-sleep.patch](../patches/tvservice-temperature-sleep.patch). Вона розрахована на дизасембльований оригінальний APK:

```text
SHA-256: a596d7f33fab2723b20870ab1f7a415be6f7df7f7266cc641c2ab7534043181b
Пакет: com.toptech.tv.service
Шлях: /system/app/TvService/TvService.apk
```

Diff не є зібраним оновленням або скриптом встановлення. В інших версіях можуть відрізнятися мітки й регістри. Не застосовуйте його до приблизно схожого APK, не вимикайте весь сервіс і не прибирайте керування обладнанням чи температурою.

### Підпис і системна інтеграція

Зміна `classes.dex` робить підпис початкового вмісту APK недійсним. Перевірений пакет використовує спільний `android.uid.system`, тому підписання стороннім ключем не є звичайною заміною. Штатна повна перевірка очікувано відхилила змінений вміст.

В Android 9 є окремий шлях зчитування сертифікатів для довірених системних пакетів під час [сканування системного розділу](https://android.googlesource.com/platform/frameworks/base/+/android-9.0.0_r1/services/core/java/com/android/server/pm/PackageManagerService.java#8831). На цьому пристрої перевірка без встановлення прийняла оригінал звичайним шляхом, а кандидат — системним, зі збереженням ідентичності пакета, shared UID і метаданих OEM-сертифіката. Пізніше фактичний новий запуск зареєстрував і запустив змінену постійну системну службу. **Самої перевірки парсером було б недостатньо для підтвердження безпечного завантаження.**

Це не створює коректно підписаного OEM-оновлення й не дає приватного ключа виробника. Перевірене встановлення було контрольованою root-модифікацією системного розділу зі збереженням оригінального APK для відкату. Глобальні перевірки APK не вимикалися. Інша прошивка може відхилити такий підхід.

## USB-режим завантаження та зникнення Wi-Fi

Внутрішній Wi-Fi використовував USB Realtek `0bda:d723` і модулі `8723du` та `cfg80211`. У невдалому запуску були відсутні адаптер, модулі й `wlan0`; після цього supplicant завершувався через відсутній інтерфейс `nl80211`. Проблема виникала на етапі виявлення обладнання / драйвера, до використання облікових даних Wi-Fi.

Vendor-конфігурація пов'язує USB-налагодження з USB-режимом наступного запуску:

| Файл | Заводський вміст або призначення |
| --- | --- |
| `/vendor/etc/adb_enable_on.ini` | Секція `[ADB_USB]` з `BOOT_ARGS = "USB_OTG_SOFTWARE_ID=device";` |
| `/vendor/etc/adb_enable_off.ini` | Секція `[ADB_USB]` з `BOOT_ARGS = "USB_OTG_SOFTWARE_ID=host";` |
| `/vendor/tvconfig/config/adb/adb_enable.ini` | Постійний boot-конфіг, до якого vendor init копіює ці джерела |

Коли `sys.usb.config` ставав `adb`, vendor init копіював джерело **ON** у поточний boot-конфіг. Запуск у режимі `device` приховував внутрішній Wi-Fi-адаптер цього пристрою. Завершений запуск у режимі `host` повернув адаптер, драйвери, Wi-Fi й мережевий ADB.

Зміна лише поточного файла була тимчасовою: під час старту Android знову копіював заводське `device`. Перевірена постійна зміна використала штатні **байти OFF/host для джерела ON і поточного файла**, зі збереженням власника, прав і SELinux-контекстів. Наявні властивості мережевого ADB не змінювалися; перед перевіркою запуску vendor-розділ повернули в режим лише читання. Після старту обидва файли залишилися `host`.

Це зміна політики USB-режиму. Прямий USB ADB на цьому пристрої не вдалося встановити, тому не можна розраховувати на нього для відновлення. Сліпе скидання debug-прапорців або перемикання USB-конфігурації також може прибрати доступ через мережевий / локальний ADB. Ці результати не пояснюють кожен збій Wi-Fi на інших платах.

## Вимоги до встановлення та відновлення

Запис у прошивку — окреме обслуговування. Призупиніть відео й узгодьте перерву перед перезапуском апаратної служби або проєктора. Наведена вище діагностика лише читає стан і може виконуватися під час перегляду.

1. Звірте точну прошивку, хеші джерел, доступ Android root, структуру монтувань та сумісність пакета/shared UID. До запису забезпечте офлайн-відновлення й фізичний доступ.
2. Збережіть оригінальні APK та всі змінювані INI разом із власником, правами, SELinux-контекстом і початковими параметрами монтування. Factory reset очищає дані користувача, але не повертає змінені system/vendor-файли. Сама наявність образу не доводить працездатність аварійного прошивання.
3. Використовуйте тимчасовий файл у тому самому каталозі, перевіряйте хеш і метадані та перейменовуйте атомарно. Для APK відкритий процесом старий видалений inode може блокувати перемонтування ext4 лише для читання; перед перевіркою RO потрібен обмежений перезапуск звіреного екземпляра TvService. Перевірене встановлення мало незалежні сторожі відкату поточного сеансу; після reboot ці процеси не зберігаються.
4. Після будь-якої помилки звірте обидва хеші й параметри монтування. Пізня помилка повернення RO може залишити джерело ON зміненим, а поточний INI — старим. Не називайте такий стан незміненим пристроєм, не запускайте сліпо старий hash guard і не перезавантажуйте до узгодження відомого стану. Збережіть можливість повернути початковий APK незалежно від Wi-Fi.
5. Підтвердьте справді новий запуск, реєстрацію пакета/служби, CPU, Wi-Fi/ADB та кінцеві INI, права й RO-монтування. Після цього спостерігайте звичайне користування. Успішної команди або зчитування лише сертифіката недостатньо.

**Автоматичне повернення після `adb reboot` не підтверджене.** Новий запуск зрештою перевірили, але наявні дані не дозволяють визначити, чи знадобилася фізична допомога з живленням. Враховуйте це обмеження й не перевіряйте перезапуски під час перегляду.

Постійний CPU-фікс працює на самому проєкторі. Після встановлення й перевірки на цьому пристрої йому не потрібен постійно відкритий браузер, Docker-контейнер чи процес моніторингу на ноутбуці. Цей результат не підтверджує сумісність з іншою прошивкою або встановленням Linux замість Android.
