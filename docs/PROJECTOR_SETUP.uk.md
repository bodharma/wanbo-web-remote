# Wanbo T2 Max: програми й оптимізація

[English](PROJECTOR_SETUP.md) · **Українська** · [Встановлення пульта](../README.uk.md#встановлення-і-перший-запуск)

Ці нотатки отримані на одному T2M+ з Android 9, збіркою `9.0.0-RS-20210928.1224`, номінально 1 ГБ RAM і 32-бітною ARM-системою. Це опис спостережень, а не універсальний рецепт видалення системних програм. Інші ревізії T2 Max, особливо моделі з Android 6, можуть мати інше обладнання та прошивку.

## Які програми встановити

Встановлюйте лише потрібні програми. Перевіряйте актуальні вимоги й повідомлення про безпеку за посиланнями; перевірені тут версії наведені для відтворюваності, а не як порада залишатися на старих релізах. APK можна встановити з флешки через файловий менеджер проєктора. Цей репозиторій їх не розповсюджує.

## ADB shell для команд нижче

Спочатку пройдіть [встановлення пульта](../README.uk.md#встановлення-і-перший-запуск), включно з перевіркою ідентифікатора проєктора. У каталозі репозиторію відкрийте тимчасову оболонку з тим самим volume ADB-ключів:

```sh
docker compose run --rm --no-deps --entrypoint sh remote
adb connect "$PROJECTOR_HOST:$PROJECTOR_PORT"
export ANDROID_SERIAL="$PROJECTOR_HOST:$PROJECTOR_PORT"
adb shell getprop ro.serialno
adb shell getprop ro.product.cpu.abi
adb shell getprop ro.build.version.sdk
```

Перевірте відповідність серійного номера своєму `.env`. Перевірений пристрій повертає `armeabi-v7a` та API `28`. Решту команд `adb` виконуйте в цій оболонці; `exit` закриє її. Не публікуйте вивід без редагування: серійні номери, акаунти, локальні адреси та журнали можуть бути персональними.

## Збережіть доступ до Wi-Fi й можливість повернення

Перед зміною Home перевірте відкриття штатних налаштувань Wi-Fi:

```sh
adb shell am start -a android.settings.WIFI_SETTINGS
```

Тримайте фізичний пульт і поточне ADB-з'єднання доступними. Для налаштування лаунчера не змінюйте Wi-Fi, не вимикайте Android Settings і не перезавантажуйте проєктор. Не вимикайте пакети масово: за неочевидною назвою може стояти керування обладнанням проєктора.

На цій прошивці USB-конфігурація ADB також впливала на USB-режим наступного запуску й могла приховати внутрішній Wi-Fi-адаптер. Перед постійними змінами ADB або прошивки прочитайте [результати перевірки USB-режиму й вимоги до відновлення](FIRMWARE_TUNING.uk.md).

## Швидші переходи

Збережіть початкові значення приватно:

```sh
adb shell settings get global window_animation_scale
adb shell settings get global transition_animation_scale
adb shell settings get global animator_duration_scale
```

Встановіть для трьох масштабів анімації значення `0.5`:

```sh
adb shell settings put global window_animation_scale 0.5
adb shell settings put global transition_animation_scale 0.5
adb shell settings put global animator_duration_scale 0.5
```

Це скорочує переходи, але не виправляє зайнятий CPU чи несправний декодер. Для повернення запишіть попередні значення; якщо було `null`, використайте `settings delete global KEY`.

## Легший головний екран

Встановіть Lite TV Launcher, відкрийте його та виберіть типовим застосунком Home. Перевірте кнопку Home, запуск програм і доступ до Wi-Fi, перш ніж щось вимикати. На перевіреному пристрої PSS легкого лаунчера становив приблизно 26–46 МіБ проти 58–78 МіБ штатного; це окремі вимірювання, а не гарантія швидкодії.

Перевіряйте вибраний Home з обома категоріями:

```sh
adb shell cmd package resolve-activity --brief \
  -a android.intent.action.MAIN \
  -c android.intent.category.HOME \
  -c android.intent.category.DEFAULT
```

Залишайте `CATEGORY_DEFAULT`: запит лише з HOME порушував вибір типового Home на цій прошивці. Результат має вказувати на новий лаунчер.

Саме на цій прошивці штатний Home watcher повертав старий головний екран. Після перевірки заміни й можливості повернення допомогло вимкнення **лише** `com.zeasn.whale.open.launcher.technical` для користувача 0 зі збереженням даних:

```sh
adb shell pm disable-user --user 0 com.zeasn.whale.open.launcher.technical
```

Це необов'язковий крок для конкретної прошивки. Не підставляйте вгадану назву пакета. Повернення штатного лаунчера:

```sh
adb shell pm enable --user 0 com.zeasn.whale.open.launcher.technical
```

## Jellyfin через Kodi

Спочатку перевірте звичайне відтворення з апаратним декодуванням. На перевіреному пристрої vendor-декодер H.264 `OMX.MS.AVC.Decoder` давав помилку і в Jellyfin, і в Kodi. Спрацював такий запасний варіант:

1. У Kodi відкрийте **Settings → Player → Videos**, змініть рівень налаштувань на **Advanced** або **Expert** і знайдіть **Processing**.
2. Вимкніть **Allow hardware acceleration — MediaCodec (Surface)** та **Allow hardware acceleration — MediaCodec**.
3. У Jellyfin for Android TV увімкніть **Playback → Advanced → Use external player**.
4. Запустіть відео з Jellyfin на проєкторі та виберіть **Kodi → Always** у діалозі Android.
5. Перевірте короткий фрагмент перед довгим переглядом. Тут працював зразок 720p / 25 fps H.264 + AAC із програмним декодуванням; важчі відео, 1080p/4K і синхронізація прогресу зовнішнього програвача не перевірялися.

Програмне декодування сильніше навантажує CPU. Якщо апаратне відтворення працює, залишайте його ввімкненим. Для повернення увімкніть обидва параметри прискорення Kodi та вимкніть зовнішній програвач у Jellyfin.

Jellyfin Android TV 0.19.10 також завершувався з помилкою, коли команда **Play on** із вебклієнта запускала зовнішній програвач: бракувало `FLAG_ACTIVITY_NEW_TASK`. Локальна кнопка Play працювала. Кнопки цього пульта керують інтерфейсом проєктора й оминають саме цей шлях дистанційного запуску; Jellyfin вони не патчать. Новіші версії клієнта можуть поводитися інакше. Зменшення ліміту бітрейту не примусить сервер транскодувати файл, який уже нижче цього ліміту.

## JellyCon: Jellyfin усередині Kodi

JellyCon дає ще один спосіб вибору відео: перегляд бібліотеки й запуск залишаються всередині Kodi без діалогу вибору зовнішнього програвача Android. Повна бібліотека сервера не імпортується в базу Kodi.

1. Встановіть [офіційний репозиторій Jellyfin для Kodi](https://jellyfin.org/docs/general/clients/kodi/), потім виберіть **Install from repository → Jellyfin Kodi Add-ons → Video add-ons → JellyCon**. Для Kodi 19 і новіших потрібен репозиторій Python 3.
2. Відкрийте JellyCon, виберіть або введіть LAN-адресу сервера й увійдіть. Підтримується Quick Connect: підтвердьте показаний код у вже авторизованому клієнті Jellyfin. Кожен проєктор налаштовується окремо; облікові дані не входять до цього пульта.
3. Додайте JellyCon до **Favourites** у Kodi для зручного доступу. Вибирайте потрібну серію всередині JellyCon; якщо vendor-декодер не працює, залишайте описане вище програмне декодування.

Перевірений ZIP репозиторію ще посилався на застарілий `repo.jellyfin.org` і повертав HTTP 404. Якщо це сталося, перевірте `repository.jellyfin.kodi/addon.xml` у ZIP і перед встановленням змініть лише три поля адрес: `info` на `https://kodi.jellyfin.org/py3/addons.xml`, `checksum` на `https://kodi.jellyfin.org/py3/addons.xml.md5`, `datadir` на `https://kodi.jellyfin.org/py3`. Збережіть структуру каталогу доповнення й решту файлів. Це актуальні офіційні адреси репозиторію Python 3, а не репозиторій цього проєкту.

У Kodi 20.2 також спостерігався нативний збій `SIGILL` у `_armv7_tick` з `libkodi.so`. Після оновлення до офіційної 21.3 зі збереженням налаштувань коротке відтворення через JellyCon і перезапуск застосунку пройшли без повторення цього збою. Довгий перегляд і повне перезавантаження проєктора не перевірялися.

## LocalSend: файли з ноутбука

1. Встановіть офіційний LocalSend на обидва пристрої. Для цього проєктора потрібен APK **android-arm32v7**; версія 1.18.2 вимагає Android 7 або новішого. Підключіть пристрої до однієї локальної мережі й відкрийте LocalSend на проєкторі.
2. На ноутбуці виберіть **Send → File**, файл і назву проєктора, показану в LocalSend. Автоматично створена назва може відрізнятися від моделі Android.
3. На проєкторі натисніть **Accept**. Надайте доступ до файлів, коли його попросить Android; типова папка отримання — **Download**. Залишайте Quick Save вимкненим, щоб підтверджувати наступні передавання. Якщо D-pad незручний для певної кнопки, скористайтеся вказівником браузерного пульта.

Перевірено виявлення проєктора з Mac і передавання невеликого текстового файлу UTF-8 з Mac на проєктор через шифрований протокол LocalSend; SHA-256 отриманого файлу збіглася. Великі файли, швидкість і зворотний напрямок не перевірялися. Ці програми не входять у Docker-образ пульта; окремої кнопки швидкого запуску LocalSend у пульті немає.

## Kodi повторює стару серію

Kodi 20.2 може після завершення процесу відновити завдання Android із URL попереднього відео. На перевіреному пристрої спочатку відкривалося посилання на нову серію, а під час запуску його замінювало старе. Це окрема проблема від описаного вище збою дистанційного запуску Jellyfin.

1. У браузерному пульті натисніть **«Перевірити Kodi»**. Посилання на відео в стартовому завданні вказує на можливе джерело проблеми, але не означає, що кожне таке завдання несправне.
2. Призупиніть або зупиніть відтворення й натисніть **«Відновити Kodi»**. Backend повторно перевірить стан, завершить лише Kodi та відкриє його головний екран із новим завданням, якщо відновлення потрібне. Налаштування, акаунти й медіафайли зберігаються. Поточна сесія призупиненого відео закривається.
3. Поверніться до Jellyfin і виберіть серію знову. Повторне відновлення вже чистого завдання нічого не змінює.

Відновлення відмовляється працювати під час відтворення, буферизації, за відсутності Kodi або нерозпізнаного формату діагностики Android. Перевірка й відновлення — явні дії; відкриття сторінки, підключення та звичайний швидкий запуск Kodi нічого не скидають. Розбір завдань і медіасесій перевірено на цій прошивці Android 9. Це дія відновлення, а не патч коду Kodi чи гарантія від повторення після перезавантаження / видалення завдання. Тести до й після зміни використовували різні URL тієї самої дозволеної серії, зокрема після завершення процесу; повне перезавантаження проєктора не перевірялося.

## Циклічне повернення до входу в Google Play

Перевіряйте встановлені пакети: невидимий у лаунчері Google-компонент не обов'язково відсутній.

```sh
adb shell dumpsys package com.android.vending
adb shell dumpsys package com.google.android.gms
adb shell dumpsys package com.google.android.gsf
```

На цьому пристрої оновлення старої версії Google Play services відновило вхід. Це спостереження не визначає причину кожного циклу логування. Оновлення має відповідати встановленому Google-компоненту, його підпису та ABI/API пристрою; віддавайте перевагу штатному механізму оновлення. Не встановлюйте випадкові GApps-набори, не починайте з очищення акаунтів і не шукайте Google APK в цьому репозиторії. Vendor WebView мав інший підпис, ніж Google WebView, тому звичайний Google APK не був прямою заміною.

## Межі оптимізації штатної прошивки

`com.toptech.tv.service` / TvService на перевіреній прошивці займав приблизно одне ядро CPU у циклі контролю температури. Він також керує обладнанням проєктора. **Не вимикайте весь сервіс, не зупиняйте термозахист і не замінюйте його універсальним Android TV-сервісом.** Його перезапуск також може змінювати доступність ADB.

Пізніше для цієї прошивки перевірили модифікацію з паузою 100 мс у циклі та збереженою гілкою захисту при 80°C. Після нового запуску й 15 хвилин спостереження медіана CPU TvService становила 0,19% одного ядра. У [нотатках про прошивку](FIRMWARE_TUNING.uk.md) є source-diff, результати, обмеження підпису та зв'язок USB-режиму з Wi-Fi. Готові образи прошивки й змінені APK тут не поширюються; Docker-образ цієї модифікації не виконує.

Для стійких зависань збережіть приватно короткі виводи `adb shell top -b -n 1`, `adb shell dumpsys meminfo` та `adb logcat -d` біля моменту збою; перед подальшими змінами визначте процес або помилку декодера. Переглядайте й очищайте журнали від персональних даних перед публікацією. Ці зміни покращують користування в межах штатної прошивки; сумісність з іншою прошивкою або Linux вони не підтверджують.
